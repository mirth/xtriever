# Phase 1 Data Model: iOS Build Spike

**Feature**: `001-ios-build-spike` | **Date**: 2026-09-10 | **Plan**: [plan.md](./plan.md)

> **[ADR-0001](../../docs/adr/0001-pin-candle-0-9-2.md) and
> [ADR-0002](../../docs/adr/0002-unsafe-mmap-safetensors-measurement.md) were accepted 2026-09-10**,
> so the dependency versions and the `load_path` comparison below are settled, not provisional.

Two groups of entities, and they should not be confused:

- **Fixture entities** are committed data, versioned in git, identical on host and device.
- **Report entities** are produced by a run and written into the spike report.

Nothing here is a persisted production format. The tantivy index is a throwaway artifact of the run
and deliberately carries no header, embedder fingerprint or format version — defining those is the
lexical spec's job (see the plan's Principle VI row).

---

## Fixture entities

### `FixtureCorpus`

The 1,000 documents, the one query, and the one sentence. Committed; generated by
`reference/gen_001_fixtures.py` from a fixed seed so it is reproducible from source.

| field | type | rules |
|---|---|---|
| `documents` | ordered list of `FixtureDocument` | exactly 1,000; order is significant and is the insertion order |
| `query` | string | non-empty; MUST match at least one document, so that an empty ranking is a real failure rather than a vacuous pass (spec edge case) |
| `sentence` | string | non-empty; the single string embedded by the embed operation |
| `seed` | integer | recorded in the fixture file; regenerating with it reproduces the corpus byte-for-byte |

### `FixtureDocument`

| field | type | rules |
|---|---|---|
| `external_id` | string | unique across the corpus; stable across regeneration; opaque to every backend (Principle V) |
| `text` | string | one to three sentences (spec Assumptions); ASCII-only, so tokenizer behaviour is not entangled with Unicode normalisation on the first run |

**Insertion-order invariant.** Documents MUST be added to the index in list order, with a
single-threaded writer. This is what makes tantivy's internal `DocId` assignment deterministic and
therefore what makes `ExpectedRanking` comparable at all (research D5). A parallel or reordered
insert silently invalidates the golden ranking.

### `PinnedModel`

Identifies the weights exactly, satisfying FR-016.

| field | type | value / rules |
|---|---|---|
| `repo` | string | `sentence-transformers/all-MiniLM-L6-v2` |
| `revision` | string | `1110a243fdf4706b3f48f1d95db1a4f5529b4d41` |
| `weights_bytes` | integer | `90868376` — asserted at load time; a mismatch is a hard error, never a warning |
| `weights_sha256` | string | recorded on first download and asserted on every subsequent run |
| `dtype` | enum | `f32` (FR-033). Asserted from the safetensors header, not assumed |
| `embedding_dim` | integer | `384` |
| `max_sequence_length` | integer | `256` — **overrides** the 128 baked into `tokenizer.json` (research D6) |
| `pooling` | enum | `mean` — attention-mask-weighted |
| `normalize` | bool | `true` — L2 |

Relationships: `PinnedModel` is the input to both `ExpectedTokens` and `ExpectedEmbedding`. Changing
any field invalidates both goldens, and the acceptance tests must fail loudly rather than
regenerate them.

### `ExpectedTokens`

The reference tokenization of `FixtureCorpus.sentence`. Checked **before** `ExpectedEmbedding`, so a
tokenizer disagreement can never be misread as an embedding failure (research D6).

| field | type | rules |
|---|---|---|
| `input_ids` | list of integers | exact equality required — no tolerance |
| `attention_mask` | list of integers | exact equality required |
| `token_type_ids` | list of integers | all zeros for a single-segment sentence; required by candle's `forward` |

### `ExpectedEmbedding`

| field | type | rules |
|---|---|---|
| `vector` | list of 384 floats | compared within tolerance, not for equality |
| `cosine_min` | float | `0.9999` (spec Assumptions) |
| `max_abs_diff` | float | `1e-3` |

The tolerance is only defensible because the weights are fp32 (FR-033); a quantised variant would
require a looser band and a weaker oracle.

### `ExpectedRanking`

The host-produced golden ranking, and the oracle for FR-014.

| field | type | rules |
|---|---|---|
| `hits` | ordered list of `RankedHit` | compared for **exact** equality against the device result — order, ids and scores |
| `k` | integer | the top-k limit used; identical on host and device |
| `writer_threads` | integer | `1`; recorded in the fixture because the ranking is only reproducible at this value |

**Why exact and not tolerant**: Principle VI promises that the same index, query and config yield
identical results. A tolerance here would hide precisely the class of bug the spike is looking for.
No tantivy documentation guarantees bit-identical scores across platforms (research risk R6), so if
this comparison fails it is itself a Principle VI finding — not a reason to relax the comparison
(FR-028).

## Boundary entities

These cross the FFI. Field-level shapes are in
[contracts/ffi-surface.md](./contracts/ffi-surface.md).

### `RankedHit`

| field | type | rules |
|---|---|---|
| `external_id` | string | the document's `FixtureDocument.external_id` — resolved from a tantivy stored field. Backends never see it (Principle V) |
| `score` | f32 | tantivy's BM25 score. `k1 = 1.2`, `b = 0.75` are private constants in tantivy 0.26.2 and not configurable, so no scoring config can drift |
| `segment_ord` | u32 | recorded because tantivy breaks ties by ascending `DocAddress` = `(segment_ord, doc_id)`, not by `DocId` |
| `doc_id` | u32 | tantivy's internal dense `u32` |

Carrying `segment_ord` and `doc_id` outward is a diagnostic decision, not an API proposal: when a
ranking mismatch happens, they are the difference between "iOS scores differently" and "iOS assigned
documents to segments differently". The production surface would not expose them.

### `Measurement`

One recorded number. FR-017 through FR-019.

| field | type | rules |
|---|---|---|
| `operation` | enum | `index`, `query`, `embed`. **Originally specified with a separate `model_load`, which was never implemented** — `spike_embed` does tokenize + load + infer in one call and FR-006 caps the FFI at three operations, leaving no seam to time them apart. See finding F-012 |
| `wall_nanos` | u64 | from `clock_gettime_nsec_np(CLOCK_UPTIME_RAW)` (research D11) |
| `footprint_bytes` | u64 | `phys_footprint` immediately after the operation |
| `footprint_delta_bytes` | i64 | change across the operation — what this operation itself cost |
| `cumulative_peak_bytes` | u64 | process-**lifetime** high-water mark as of this row. Not a per-operation peak: the value is monotonic, so only the maximum across a run is meaningful as a verdict input |
| `peak_method` | enum | `ledger` or `sampled`, whichever produced `cumulative_peak_bytes`. `proc_pid_rusage`/`ri_lifetime_max_phys_footprint` is **not reachable from Swift on iOS** (research risk R1 confirmed), so the source is `task_vm_info.ledger_phys_footprint_peak` cross-checked against sampling |
| `memory_is_valid` | bool | `false` if either `task_info` call failed. A run containing an invalid measurement yields `UNTESTED`, never a verdict — otherwise a failed syscall reads as 0 bytes and passes the ceiling |
| `available_before` / `available_after` | u64 | `os_proc_available_memory()`, which lets the device's own limit be derived. **Zero on the Simulator**, which Apple documents as returning 0 for a non-app process |
| `load_path` | enum | `buffered` or `mmapped` — set on the `embed` rows; the ADR-0002 comparison |

### `DeviceRun`

One execution of the whole harness on one device. FR-019, FR-022.

| field | type | rules |
|---|---|---|
| `run_id` | string | distinguishes the repeated runs FR-022 requires |
| `device_model` | string | recorded, never generalised across device classes |
| `ios_version` | string | |
| `build_config` | string | MUST be `Release` with "Debug executable" off, coverage and sanitizers disabled (research D11) |
| `thermal_state` | enum | `ProcessInfo.thermalState` at run start |
| `rayon_num_threads` | string | MUST be `"1"`; a run with anything else is `UNTESTED`. **The variable is `RAYON_NUM_THREADS`** — candle 0.9.2 reads that, *not* `CANDLE_NUM_THREADS`, which later versions read and which research D15 first recorded in error. Setting the wrong one leaves the pool sized by the device's cores while the record claims it was pinned |
| `observed_memory_limit_bytes` | u64 | derived; **distinct from the 300 MB constitutional ceiling** and must not be conflated with it |
| `measurements` | list of `Measurement` | |
| `ranking` | list of `RankedHit` | compared against `ExpectedRanking` |
| `embedding` | list of 384 floats | compared against `ExpectedEmbedding` |
| `terminated_by_os` | bool | if true, the memory verdict is FAIL and the run is still recorded (FR-025, spec US3 scenario 6) |

### `BinarySizeReport`

FR-018, measured per research D10.

| field | type | rules |
|---|---|---|
| `installed_uncompressed_bytes` | u64 | from `App Thinning Size Report.txt`; this is the **only** number that means "installed on device" |
| `download_compressed_bytes` | u64 | from the same report |
| `rust_staticlib_bytes` | u64 | attributed via the link map (`LD_GENERATE_MAP_FILE`) |
| `model_weights_bytes` | u64 | expected `90868376`; a resource, not part of the executable |
| `variant` | string | the thinning variant the numbers belong to |

The `.app` bundle, the `.xcarchive` and the `.ipa` are explicitly **not** valid sources here — Apple
states none of them is suitable for measuring app size.

## Report entities

### `FeatureSetMatrix`

FR-001, FR-002. One row per crate per target — 4 crates × 2 iOS triples = **8 verdicts minimum**
(SC-001), plus host rows.

| field | type | rules |
|---|---|---|
| `crate_name` / `resolved_version` | string | resolved versions recorded, never assumed (FR-004) |
| `target` | string | one of the triples; a pass on one is never reported as a pass on both |
| `features_enabled` / `features_disabled` | list of strings | |
| `native_dep_avoided` | string, optional | the C/C++ dependency a disabled feature would have pulled, e.g. `columnar-zstd-compression → zstd-sys` |
| `verdict` | enum | `pass`, `fail`, `untested` — never empty (FR-024) |

### `Finding`

FR-025 through FR-027.

| field | type | rules |
|---|---|---|
| `item` | string | the FR or acceptance scenario that did not pass |
| `observed` | string | what actually happened |
| `evidence` | string | log excerpt, error code, or measurement |
| `smallest_reproduction` | string | required — a finding without one is incomplete |
| `adr` | path, optional | required when the finding constrains a future design decision |
| `workaround_applied` | string, optional | if present, the report MUST NOT show the item as an unqualified pass (FR-027) |

### `SpikeReport`

The close-out artifact. Holds one `FeatureSetMatrix`, at least two `DeviceRun`s, one
`BinarySizeReport`, and all `Finding`s.

**Completeness invariant (SC-008)**: every item in FR-001–FR-022 appears with a verdict; every `fail`
has a `Finding`; every design-constraining `Finding` has an `adr`. This is checkable mechanically and
should be, rather than left to review.

## State transitions

Only one entity has meaningful state — the per-item verdict, which moves in one direction:

```
untested ──► pass
         └─► fail ──► Finding ──► (ADR if design-constraining)
```

There is no `fail → pass` transition within a run. A failing item is re-measured only after a code
change on a new commit, and both results are kept. Overwriting a `fail` with a later `pass` on the
same commit is the exact behaviour FR-028 and Agent Operating Rule 6 forbid.
