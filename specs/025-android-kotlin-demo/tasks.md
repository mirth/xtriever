# Tasks: The Android Kotlin Wikipedia Demo

**Input**: Design documents from `/specs/025-android-kotlin-demo/`

**Prerequisites**: [plan.md](plan.md), [spec.md](spec.md), [research.md](research.md),
[data-model.md](data-model.md), [contracts/](contracts/), [quickstart.md](quickstart.md)

**Tests**: included and written first. Principle II and Agent Operating Rule 4 make them
mandatory here: every user story's tests are committed failing before its implementation.

**Organization**: by user story, in the spec's priority order. Two pull requests: **PR A** is
Phases 1–3 (the module and its proof), **PR B** is Phases 4–7 (the demonstration). Each stays
under Rule 3's ~800 changed lines.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: can run in parallel — different files, no dependency on an unfinished task
- **[Story]**: the user story the task serves
- Every task names the file it touches

## Path Conventions

`android/xtriever/` is the library module, `apps/android-wiki-demo/` the application, both
outside the Cargo workspace; `scripts/` holds the packaging script; `docs/adr/` the decision
record. One Gradle build is rooted at the repository root so the quickstart's
`./gradlew :android:xtriever:…` commands work.

emulator reproduces `swift/Xtriever/Tests/Fixtures/expected.json` at re-rank depths 0, 5, 10
and 20.

### Implementation for User Story 1

- [ ] T011 [US1] Write `android/xtriever/src/main/kotlin/.../XtrieverIndex.kt`, the wrapper mirroring `swift/Xtriever/Sources/Xtriever/XtrieverIndex.swift`: open with a load path, hold the paths, the open and model-load times and the engine's index information, close deterministically, and add no capability the Swift wrapper lacks (FR-001)
- [ ] T012 [US1] Teach `scripts/build-android-package.sh`'s `--with-fixtures` to build and stage the 40-document fixture index and its goldens for the instrumented test, as the iOS script does for the simulator
- [ ] T013 [US1] Make `android/xtriever/src/androidTest/kotlin/.../FixtureParityTest.kt` pass on the emulator; if any score bit differs, stop and report — never widen a tolerance (Rule 6)

- [ ] T015 [P] [US1] Write `android/xtriever/README.md`: what the module is, the one command that builds it, the processor and operating-system requirements, and what a consumer must provide (real files, format version 2)

## Implementation Strategy

### MVP (User Story 1 only)

Phases 1 to 3 give a reusable module proven against the committed goldens on a real Android
runtime. That is the platform claim; stop there, merge PR A, and the demonstration becomes
optional work rather than a prerequisite.

### Incremental Delivery

PR A: the module, the script, the decision record. PR B: search, then preparation and the
explanatory screens, then the record. Each phase ends somewhere the emulator can be pointed at.

## Notes

- Every instrumented task runs on `xtriever-arm64`, the prepared emulator; check
  `fphp asimdhp` in its processor features first, or the failures will be illegal instructions
  rather than assertions (quickstart Step 0).
- Nothing generated is committed: bindings, native libraries, staged assets and Gradle outputs
  are all ignored and reproduced by one command.
- No continuous-integration job is added. The existing `cargo check --workspace --target
  aarch64-linux-android` stays exactly as it is (FR-015).
- The owner commits, pushes and merges at every ⛔ checkpoint.
