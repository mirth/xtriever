## Verdict

`pip install` of a wheel built by one command gives a Python program the whole engine: open,
search with explanations and the stage report, and — the owner's Q1 = B — build an index from
its own documents. Every number is the engine's: the 16 golden pairs of the 007 fixture are
bit-identical from Python (fused f64, re-rank f32, bm25/dense feature bits, ranks), and an
index built from Python over the 005 fixture's documents reproduces the same goldens on every
query (SC-007), both through the Rust FFI suite and through the installed package. Every
engine error kind is its own Python exception under one base; the interpreter lock is
released during engine calls (a thread's 20 × `sum(range(100_000))` finishes in ~24 ms during
a ~430 ms search); the binding costs a median 0.36 % of the engine's own time. The module is
generated by uniffi from the crate's exports — nothing generated is committed — and maturin
packs it; the same exports appear in the Swift package's next generation and change nothing
there (17 / 17 run, 0 failures). The engine is untouched: `xtriever-ffi` gained five wire
types and seven exports, all conversions; no pipeline, stage, core or format change.

## Findings

### F-001 — `strip = true` removes the symbol table uniffi's metadata lives in (Linux)

The first CI build produced a wheel whose `.so` the bindgen refused: "No UniFFI metadata
found". uniffi_bindgen 0.32.1 reads the metadata from the ELF **static** symbol table
(`macro_metadata/extract.rs:49`, `elf.syms`); the workspace's release profile has
`strip = true`, which drops `.symtab` on Linux while `.dynsym` survives (`nm -D` still listed
17 `UNIFFI_META_*` symbols — a misleading first check). macOS keeps exported symbols in the
dylib's export trie, which is why the research run passed. Verified in a `rust:1.91.1`
container: static symbols `wheel` profile 17, `release` 0. Fix: `[profile.wheel]` inheriting
release with `strip = "debuginfo"`, selected in `pyproject.toml`; the iOS staticlib is
unaffected (archives keep their symbols).

### F-002 — `setup-uv` with `python-version` creates the venv itself

The job's first run failed on `uv venv .venv`: the action had already created `.venv` and
exported `VIRTUAL_ENV`. The step now only installs into it.

### F-003 — The host's default `python3` is x86_64

`/usr/local/bin/python3` (Homebrew under Rosetta) cannot load the arm64 library
(`incompatible architecture`); the arm64 interpreters under `/opt/homebrew` and `uv`'s
managed CPython work. The README states it; the quickstart names the interpreters.

### F-004 — `maturin -m` is the Cargo manifest, not the pyproject

The build command is run from `python/` (`cd python && maturin build`); `maturin build -m
python/pyproject.toml` fails with "the manifest-path must be a path to a Cargo.toml file".
The quickstart, tasks and contract were corrected.

### F-005 — A debug build of `gemm-f16` fails on aarch64 Linux

In the arm64 container, the bindgen bin's dev-profile build failed with "instruction
requires: fullfp16" from `gemm-common`'s inline assembly; the release/wheel profiles built.
CI is x86_64 and unaffected; noted for anyone building the Python package on an arm64 Linux
box (use `--profile wheel` for the bin too, or a newer `gemm`).
