# Report: The iOS Wikipedia Demo App

**Feature**: `009-ios-wiki-demo` | **Date**: 2026-09-14 | **Spec**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

## Verdict

The demo exists and does what the three features were for: on an iPhone 16e in airplane mode,
a person searches all of Simple English Wikipedia through the whole pipeline and watches it
work — the fused list in **339 ms** (median), the re-ranked order replacing it with what moved
**2.3 s** later, every hit explaining itself under the engine's feature names, the engine's
stage report on screen, the corpus's identity and the CC BY-SA attribution one tap away. The
full app peaks at **546.4 MB against the 600 MB ceiling — PASS**, 10 MB above the bare
harness on the same index (008). The app owns no retrieval logic: its tests prove the hits it
shows are the engine's bit for bit (fused = the 007 goldens without a re-ranker, re-ranked =
with one), that a second submission cancels the first 20 / 20 times, that the main thread keeps
its cadence, and — driven as a finger would on the simulator — that the screens show it.
Nothing under `crates/`, `swift/Xtriever/Sources/` or `.github/` changed. Retrieval quality of
the corpus remains unmeasured (008, owner decision) and the About screen says so.

## What was built

`apps/ios-wiki-demo/` — an xcodegen project (the harness's shape), one `@MainActor`
`ObservableObject` (`DemoModel`: preparation → warm-up → ready; submit = fused search, then
re-ranked search, cooperative cancellation between and after; change marks; settings) and seven
SwiftUI views (preparation, search with a bottom toolbar, hit row, hit detail, stage report,
settings, about). ~760 lines of app Swift, ~480 of tests, one UI walk. Staged and generated by
`scripts/build-ios-package.sh … --demo`.

## Findings

### F-001 — XCUITest's synthesized tap does not push a row while the search field is active; a finger does

With `.searchable` active (the state after submitting — "Cancel" showing), a synthesized tap on
a row inside the list did not push the detail screen, twice, with identical before/after
screenshots; the owner confirmed a real tap opens the detail with its "Why this hit" section.
The UI walk therefore covers search, the report, Settings, About and the empty case, and leaves
the row tap to the hand walk (T028). Recorded rather than worked around with coordinates.

### F-002 — The test host must not open the engine; two tests in one process double the footprint

The demo app is its own test host (device tests need an application). Two contaminations
surfaced in sequence: `AboutTests` running before the measurement in the same process left its
`DemoModel` (index + models, ~500 MB) alive — baseline 746 MB; and the host app's own
`RootView.task { start() }` opened a second index for the measurement's process — after open
1,057 MB. Fixes: the measurement runs alone in its process (quickstart), and `WikiDemoApp`
shows a placeholder when `XCTestConfigurationFilePath` is set (XCUITest launches the app as a
separate process without it, so the UI walk still drives the real app). The bad records were
not committed; the latencies they showed (median total 2.69–2.71 s) agree with the clean run.

### F-003 — iOS hides navigation-bar items while the search field is active

The first layout put Settings and About in the navigation bar; after a submission (search
active, "Cancel" showing) they vanished, and Cancel clears the results. Moved to a bottom
toolbar, which stays. Found by the UI test, not by eye.

### F-004 — `@testable import` needs `ENABLE_TESTABILITY` in Release for the measurement scheme

007 F-005 again, from the other side: the measurement must test a Release build (`Measure`
refuses a verdict on Debug) and the app's tests `@testable import` the app. The app target sets
`ENABLE_TESTABILITY: YES` for Release — `-O` stays; internal symbols become visible to the test
bundle. The measured numbers agree with the harness (no testability there), so it costs nothing
observable.

### F-005 — With both indexes staged, the model tests must pin the fixture

`DemoModel` prefers the Wikipedia index when it is bundled, so a build staged with `--with-wiki`
ran the goldens tests against 427,947 passages — 535 mismatches, all correct behaviour. The
model takes a `corpus:` selector (`.preferWikipedia` default, `.fixture` for the tests); the
device record was taken before this test-only parameter existed and the default path is the
one measured. The suite now passes with either staging: 15 / 15 with both.

## Known costs (stated, not claimed small)

- The fused-first design runs the lexical and dense stages twice per query (D2): ~0.34 s of
  the 2.66 s median. A "re-rank this list" entry point would remove it — an engine change.
- The maximum total per query (3.05 s) is over SC-001's 3 s; the median (2.66 s) is what the
  criterion measures, and the max is one query on a nominal-thermal phone.
- Half a gigabyte resident after open, of which ~200 MB is the id map held twice (008 F-002).
- Retrieval quality of the corpus is unmeasured; the demo makes no claim about it.
- Sideload only: 1.26 GB of resources.
